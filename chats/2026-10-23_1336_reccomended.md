The facts change one premise in the issue, so here it is before the questions.

**The 502 in the issue probably never happens on first boot.** The frontend has `depends_on: backend: service_healthy`, and #15 moves the backend's healthcheck to `/ready`. The backend also waits for `ollama-pull` to finish. So during a slow first download the frontend container hasn't started: the browser gets *connection refused* on :8080, and the reviewer is watching `pixi run up --wait` in the terminal. In Compose, a 502 or an unready index only shows up once the page is already open: during `pixi run reindex`, after a backend restart, or if the backend dies (there's no restart policy). In dev mode (`dev-frontend` + `dev-backend`) it can happen at any time.

The `llm` states can come up at any point while the app runs: a revoked key, a provider outage, or a model that was never pulled into a native Ollama.

---

❓ **Q1 - Who is the banner written for?** The CSM can't fix any of these states. The reviewer, who is also running the stack, can. The options:
- (a) CSM-only copy: what's wrong and whether to wait or contact support. Nothing technical.
- (b) Operator-only copy: the raw `detail`, the `ollama pull` command, and so on.
- (c) Two layers: a plain CSM headline that says whether to wait or get help, plus a collapsed **"Details for whoever runs this"** section with the check name, its `detail`, and the copyable `ollama pull <model>` command for `model_missing`.

➡️ (c). The headline stays honest with the CSM, and the reviewer gets the fix one click away. This matches the Turn error card, which already shows the `code` in small mono.

---

❓ **Q2 - When does the page poll `/ready`?** I recommend three triggers:
- on load;
- while any check is failing, every 5 s (the server caches the `llm` probe for 60 s, so this mostly re-reads cheap state);
- once after any Turn error with an operational code (`index_not_ready`, `retrieval_unavailable`, `llm_*`).

When everything is ok it stops polling, so a healthy page makes no background requests. The alternatives are to never poll and react only to Turn errors, or to poll all the time.

➡️ Yes: load, then 5 s while degraded, plus a re-check after an operational Turn error. No steady polling while healthy.

---

❓ **Q3 - Is the input disabled while a gating check fails?** I recommend this:
- While `database` or `index` is failing, **Send is disabled**, with a one-line reason by the button. Typing stays allowed, so the question is ready when the banner clears.
- While only `llm` is failing, Send **stays enabled**. The check is non-gating by design, it can be up to 60 s stale, and a failed Turn already gets a clear error card with Ask again.

➡️ Yes: disable Send (not typing) only for the gating checks, and never for `llm`.

---

❓ **Q4 - What does the reviewer see during the first slow download?** Given the fact above, the options:
- (a) Accept that the terminal is the UX. `pixi run up` already prints the ~2.7 GB hint and the `docker compose logs -f ollama-pull` command. The README states that :8080 doesn't answer until `up --wait` returns.
- (b) Start the frontend early (`depends_on: service_started`, or no dependency) so the browser shows a "starting up" banner. This means nginx can't resolve `backend` at config load and would fail to start. Working around that needs a `resolver 127.0.0.11` plus a variable in `proxy_pass`. It also breaks the meaning #15 chose: "frontend healthy = the stack can answer".

➡️ (a). Keep #15's ordering and make the terminal hint plus the README the first-boot UX. The browser banner only needs to handle "server unreachable" (a fetch error, 502 or 504 from nginx, or a non-JSON body) as a state of its own, for reindex, a dead backend and dev mode.

---

❓ **Q5 - What happens when the banner and a Turn's error card share a cause?** For example, the key is revoked, the banner says so, and the CSM sends anyway. I recommend both show: the error card is the permanent record of *that* Turn, and the banner is the *current* state of the stack. The banner sits pinned between the header and the conversation, not inside the scroll, so it doesn't push Turns around.

➡️ Yes: both show, with the banner pinned under the header.

## Readiness banner and degraded-mode UX: resolution

**Polling `/ready`**
- The page polls `/ready` on load. While any check fails, it polls every 5 s; when all checks pass, it stops.
- It also re-checks once after any Turn error with `index_not_ready`, `retrieval_unavailable` or an `llm_*` code.
- Polling pauses while the tab is hidden and re-checks as soon as the tab is visible again.

**The banner**
- There is one banner, pinned under the header and outside the scrolling conversation. It shows the most severe failing state, in this order: unreachable > `database` > `index` > `llm`.
- Colours:
  - blue: the index is still building;
  - amber: an `llm` problem;
  - red: the server is unreachable, the database is down, or an index sync is retrying after an error.
- Each banner has two layers: a CSM headline and subline, and a collapsed **"Details for whoever runs this"** section that lists every failing check. The copy is the Q8 table.
- "Unreachable" means a fetch error, a 502/504 from nginx, or a body without the readiness shape. A 503 that comes with a readiness body is read as a normal readiness result.
- When the stack recovers, the banner disappears silently. If the CSM typed a question meanwhile, focus stays in the composer.

**Gating the composer**
- While `database` or `index` fails, Send is disabled and a reason shows next to it. Typing stays allowed.
- An `llm` failure never disables Send.
- The banner and Turn error cards can show at the same time: the card records what happened to that Turn, and the banner shows the current state.

**First boot**
- In Compose, the frontend waits for a ready backend (#15), so a slow first Ollama download shows up in the terminal, not the browser.
- The terminal output is the UX for that wait: the `up` hint plus a README paragraph saying :8080 answers once `up --wait` returns.
- No nginx resolver workaround.

**Contract changes**
- The `llm` check becomes `{ok, detail?, command?}`. `detail` is limited to `auth_failed`, `unavailable` or `model_missing`, and `command` carries the `ollama pull <model>` line, which gets a copy button.
- The `retrieval_unavailable` error card is titled "The Knowledge Base can't be reached right now".

**Defaults I'm assuming (tell me if any is wrong)**
- An unknown `llm` `detail` value falls back to the amber "AI provider isn't responding" copy.
- Blue and amber banners announce politely to screen readers (`role="status"`); red ones use `role="alert"`.
- Tests: Vitest with MSW handlers for each `/ready` shape, plus a 502 and a network error, all checking what the CSM sees.
- No ADR and no new glossary terms, same as #14 and #15: all of this is cheap to change.
